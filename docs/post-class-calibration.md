# 课后校准操作流程

第一场 MasterClass 之后,拿到真实数据,决定题目、基准线、代价系数、错配判据、文案语气要不要改。
**这份只给流程与判断依据,不替任何一项做决定。** 每一项改不改,都按判断标准 19 先问:
**这个改动会不会让已经交出去的报告变成另一个意思?**

---

## 0. 先知道的三件事 —— 它们决定了「改 config 里一个数」实际意味着什么

**① 分数是存死的,报告上的其余东西是现算的。**

| 报告上的东西 | 什么时候定下来 | 改 config 并部署之后,已出分的学员 |
|---|---|---|
| 维度分、总分、档位、最弱 / 最强两维 | 出分那一刻写进 `assessment_results` | **不变**(除非专门重算) |
| 每题的徽章(满 / 部分 / 缺) | 每次打开报告,按存下的答案现算 | 跟着计分公式变 |
| 根因、30 天行动、代价金额、错配提示、下一步推荐、档位名称与说明 | 每次打开报告,按**前端里打包的 config** 现算 | **部署那一刻起全部跟着变** |
| 本期基准线、和基准的差值、「同一档 N 人」 | 每次打开报告,按**当时**的样本池现算 | 本来就在变(2026-10-08 新加一条测试数据后,同批的「18 份样本」变成了「19 份」) |
| 已生成的 PDF、分享卡 | 生成那一刻 | **不变** —— 与网页报告从此不一致 |
| GHL 里的档位字段、弱项 / 错配 / 高意向标签 | 出分时写一次 | **不变**,除非重新同步 |

**② 没有记录「这份报告用的是哪一版 config」。** 结果表里没有版本号。能用的代理:
`assessment_report_files.pdf_status_at`(PDF 生成时刻)早于改动的部署时刻 ⇒ 那份 PDF 是旧版。所以**每次部署校准改动都要记下部署时刻**。
可选的结构性修法(记版本号 / 内容指纹 / 报告快照……)列在 PROGRESS「当前未完成 ⑩」,未做决定。

**③ 「已发出的报告」不是一样东西,是四样:** 网页报告(链接一直有效、每次打开现算)、PDF、分享卡、GHL 里的字段与标签。
改动对这四样的影响各不相同(见第 5 节)。

## 1. 准备

- 本机装好 Supabase CLI、已登录、在仓库里 `supabase link` 过(和平时只读查询同一条路);Node ≥ 22.18(直接跑 `.ts`)
- 五个脚本都在 `scripts/calibration/`,**只读**(每条查询都被包进 `select * from (...)`,写语句在语法上就执行不了;另有关键词检查),
  **只输出统计**(查询里就不取姓名、联系方式、任何 id、问卷开放题原文)
- 范围参数(每次输出的第二行都会印出来):
  - 默认 = 真实学员(「不是测试批次」,含批次被删的真实学员)
  - `--scope=test` = 只跑测试批次;`--cohort=<批次 uuid>` = 只跑一个批次;`--json` = 机器可读
- **先跑一次 `--scope=test`**,确认环境通了,再跑真实数据
- 每次的输出连同时间存下来(贴进 PROGRESS 那一轮的小节)—— 改不改的依据要能被下一个人看到

## 2. 顺序 —— 按依赖关系,上游的先看

| 步 | 命令 | 看什么 | 为什么排在这里 |
|---|---|---|---|
| 1 | `npm run calib:baseline` | 先看**每个批次的样本量**,再看基准线与档位分布 | 样本量决定后面哪些结论能下;n < 10 的批次报告本来就不用本批基准 |
| 2 | `npm run calib:questions` | 每题分布、得分率、与同维其它题的相关 | 题有问题,维度分就有噪声 —— 下游的基准线、最弱维度、错配、代价全都建在维度分上 |
| 3 | `npm run calib:baseline`(再看一遍,这次看候选值) | 均值 vs 中位数 / 截尾均值;档位是否挤在一两档 | 依赖维度分 |
| 4 | `npm run calib:priority` | 现有判据 vs 候选判据的触发比例;有多少触发是平分造成的 | 依赖最弱维度 |
| 5 | `npm run calib:cost` | 每个系数 ±10% 时,有多少人的报告数字会变 | 依赖维度分与 3.0 门槛 |
| 6 | `npm run calib:actions` → Viho 审阅 `docs/review/action-library-review.md` / `.csv` | 语气 | 不依赖数据,**现在就能做** |

## 3. 每一项:看什么、什么情况下才值得考虑改

阈值只是「值得停下来看」的线,不是自动结论。**样本少于约 30 人时相关系数很不稳**,不要只凭一个批次下结论。

### 题目(`calib:questions`)
- **信号**:同一题在 ≥ 30 人的样本里「最多那项 ≥ 80%」(一边倒),**且**「r(其余)」持续 < 0.2(和同维另外两题不像在量同一件事)
- **一边倒不一定是题坏了**:它也可能就是这群人的真实情况(比如大多数人确实还没有 CRM)。要问的是「它在**我们的学员之间**分不分得开」
- **怎么改**:⚠️ **不要改已有选项的含义或个数**。答案存的是选项下标,改了之后旧答案的下标会指向新文字,
  徽章按新公式现算、而存下的维度分还是旧的 —— 同一份报告里自相矛盾。要改就**加一道新题号**(或整体升版本、旧答案按旧版解释)
- 影响面:题目文案出现在报告的「每一维为什么是这个分」与 30 天行动的「现在 → 目标」里,**网页报告部署即变**

### 基准线(`calib:baseline`)
- **信号**:多数维度「中位 − 现用」的绝对值 > 0.3,说明均值被少数极端值拉着走。(2026-10-08 用真实数据跑过一次全部四个脚本:默认批次 51 人,四维中位数比均值低 0.3–0.7。关键数字与「样本量够不够」见 PROGRESS「真实数据上的校准分析」)
- **候选**:中位数、10% 截尾均值;`min_n_for_baseline`(现在 10)
- 影响面:基准线本来就每次打开现算、本来就在随样本增加而变 —— 换算法与「多了几个人」是同一类变化,但**变化会一次性落在所有网页报告上**(虚线、差值、「你在本期后 25%」这类定位都会动);PDF 不变

### 档位区间(`calib:baseline` 末尾的档位分布)
- **信号**:多数人挤在一档(2026-10-08 那次汇总:51 人里 36 人在「手工作坊型」)
- ⚠️ **影响面最大的一项**:存下的档位不会变,新出分的人按新区间 ⇒ **同一个总分在两个人身上是两个档位**;GHL 的档位字段与 `assessment_tier_*` 标签、「同一档 N 人」都随之分裂。
  这是产品决定,不是校准参数 —— 改之前把第 5 节的选项一起定下来

### 错配判据(`calib:priority`)
- **看**:A(现有)与 B / C / D 的触发比例差多少;A 的触发里有几个是「平分时取序」造成的(那些人选的其实就是最弱之一);选了次弱的人占多少
- 现有判据有三个读者:学员报告第 7 板块的提示(现算)、GHL「方向错配」标签(出分时打的)、后台问卷洞察(现算,三分法)
- PROGRESS「C」那一节原话:要改的话是一次产品决定,而且要连已发出的报告怎么处理一起想。
  依据应当是数据 —— 比如「选了次弱的人」在开放回答里和「选了根本不弱的维度的人」有没有可分辨的差别(开放题原文脚本不取,要在后台问卷洞察里人工看)

### 代价系数(`calib:cost`)
- **看**:每个系数 ±10% 时有多少人的显示数字会变、中位数动多少;门槛 3.0 动一下时多少条出现 / 消失
- ⚠️ **测评数据本身校准不了这些系数** —— 系数是「流失率 30%」「成交率提升 8 个百分点」这类关于学员生意的假设,测评里没有结果数据。
  脚本只能说明「这个数字有多敏感」,改不改的依据要来自外部(Viho 的行业判断、学员的真实反馈)
- 影响面:金额是现算的,**部署即变**;PDF 里的旧金额不变 —— 学员手里的 PDF 和打开链接看到的金额会不一样

### 文案语气(`calib:actions`)
- Viho 在审阅稿里标出语气不对的条目;定下来的改动改进 config,不改审阅稿
- 根因三档目前**只有中文**(英文报告里显示中文,Stage 12 的已知缺口);如果这次要重写根因,可以顺手把英文一起补上 —— 那会让 `check:i18n-parity` 要不要认这种形状变成一个要一起决定的问题
- 影响面:**部署即变**;语气改动通常不改变含义,但 PDF 与网页仍会不一致

## 4. 改动怎么做版本管理

1. **一项一个分支、一个提交**,不把几项校准混在一次部署里(混了之后哪个变化来自哪项就分不清)
2. 改 config 一律经 `npm run config:apply`(先校验后落地);改完跑 `npm run verify`
3. **升 `meta.version`**,并在 `meta.changelog` 写一句改了什么、依据是哪次脚本输出:
   - 补丁号:只改文案语气
   - 次版本号:改了会让报告上的**数字或提示**变化的东西(代价系数、基准线算法、错配判据)
   - 主版本号:改了**分数本身的含义**(题目选项、计分、档位区间)
4. **改之前、改之后各跑一次相关脚本**(同一个范围),两份输出都贴进 PROGRESS —— 「改完之后多少人的报告会变」要在部署前就知道
5. **记下部署时刻**(UTC)。之后要找「哪些 PDF 是旧版」就靠它:`assessment_report_files.pdf_status_at < 部署时刻`
6. 冻结期(10/11 之后)不部署任何校准改动

## 5. 已发出的报告怎么处理 —— 选项(不做决定)

改动会改变已发出报告的含义时,下面几种做法可以单用也可以组合。**选哪一种是 Viho 的产品决定。**

| 选项 | 做法 | 学员看到的 | 代价 / 风险 |
|---|---|---|---|
| **A. 保留原版(什么都不做)** | 只部署 | 手里的 PDF 是旧版;**打开链接看到的是新版** | 零成本;但「同一份报告两个版本」—— 学员拿 PDF 和网页对照、或转发给别人时会对不上 |
| **B. 网页报告也保留原版** | 出分 / 渲染时记下 config 版本,网页报告按当时的版本渲染(需要改代码:存版本号 + 前端保留旧版 config) | 什么都不变,新规则只对之后出分的人生效 | 要开发;前端要长期带着多份 config;同一批里前后两拨人按不同规则 |
| **C. 重新生成 PDF 与分享卡** | 后台「重新生成 PDF」逐个点(每人每种语言一次)。**现在没有批量入口** —— 定时 sweep 不扫已就绪(ready)的行,批量重渲要另写 | 下次下载拿到新版;**已经下载 / 转发出去的旧 PDF 收不回来** | 每份约 10 秒 Chromium(51 人约 9 分钟,【推断】按 2026-10-08 实测的单份耗时);占 `pdf_attempts` 次数;要排除测试批次 |
| **D. 通知学员** | 经 GHL 发一条「你的报告已更新」+ 链接 | 知道有更新,会去看新版 | 一次面向全部学员的外发(要 GHL 工作流与文案);可能引来「为什么变了」的问题;必须排除测试批次 |
| **E. 同步 GHL** | 对已出分的人重新写档位字段 / 重打标签 | 学员看不到;影响销售分群与工作流 | 现有的 resync 只重试失败过的行,**全量重同步要另写**;标签变化可能触发 GHL 工作流(会不会给学员发消息要先在 GHL 里确认) |

各类改动牵动哪几样(✓ = 会出现新旧不一致):

| 改动 | 网页报告 | PDF / 分享卡 | GHL |
|---|---|---|---|
| 文案语气 | ✓(部署即变) | ✓(旧的不变) | — |
| 代价系数 / 门槛 | ✓ | ✓ | — |
| 基准线算法 | ✓(本来就在变) | ✓ | — |
| 错配判据 | ✓(第 7 板块) | ✓ | ✓(错配标签) |
| 档位区间 | 存下的档位不变,新出分的按新区间 ⇒ 批内不一致 | ✓ | ✓(档位字段与标签) |
| 题目选项 | ✓(且旧答案可能被按新文字解释 —— 见第 3 节) | ✓ | ✓ |
