# 重填功能 —— 设计方案

> 2026-10-14 写;同日 Viho 定了[三件事](#viho-的决定2026-10-14)。实施按[第 6 节](#6-分几步做每一步怎么验证工作量)分步做,每一步的状态写在那一步下面。
> **第 2 步及之后要等 Viho 盘点完 GHL 里由标签触发的工作流**(清单:[`ghl-inventory.md`](ghl-inventory.md))。
> 依据:对仓库的全量只读梳理(每一处「一个 entitlement 只有一个答题记录」的假设都列在[附录](#附录现在的代码里一个人一份的假设在哪里));
> 成本数字来自生产库的只读汇总(2026-10-14)。

## 需求(Viho)

做过测评的学员打开链接,**先看到自己最新的报告**,报告下方有「重填」按钮;重填之后报告更新或多一份,**每份都有时间记录**。

## Viho 的决定(2026-10-14)

| # | 问的是什么 | 决定 | 对方案意味着什么 |
|---|---|---|---|
| 1 | 频率限制 | **两次完成之间至少隔 24 小时;每人最多 6 份**(第一次 + 5 次重填) | 「课前做过一次、课上当场再做」这种 24 小时内的第二次**会被挡住** —— 选 24 小时就接受了这一点。「同一时间只能有一份没做完的」不是限额,是数据结构本身(第 1 节的唯一索引),照旧 |
| 2 | 历史那几份能不能「生成另一种语言」 | **只对最新那一份开放** | 历史那几份只提供已经生成好的文件下载;渲染成本的上限因此是「每份最多两种语言」,入口也只有一个要守 |
| 3 | 重填时答什么 | **背景题(P1–P3)和问卷要重新回答,但预先填好上一次的答案**,学员可以直接确认或修改;**15 道正式题从空白开始** | 预填的来源 = 最新完成的那一份;预填**只是初始值**,学员要像第一次一样提交,才算答了(没有「沿用上次」的隐式复制 —— 不提交问卷就不能出分)。新的一份存它自己的背景题与问卷,旧的一份原样不动。正式题不预填,避免照着上次的答案点一遍 |

## 先说结论

- **每次重填 = 新开一份答题记录**,旧的一份原样保留、永远不再被写。不做「把旧的那份清空重答」—— 那正是「已完成的不能再写入」那道守卫堵上的漏洞。
- **「算数」的永远是每个人最新完成的那一份**:报告默认显示它,GHL 字段与标签、基准线、批次统计、现场模式、后台名单都按它。
  「最新的一份」只在一个地方定义(一个数据库视图 + 一个取当前答题记录的函数),所有读者都从那里取。
- **第一步上线之后,对现有数据什么都不变**:今天每个人都只有一份,「最新的一份」就是那一份。这一点用上线前后的只读快照逐字比对来证明。
- 频率限制(Viho 已定):**同一时间只能有一份没做完的重填;两次完成之间至少隔 24 小时;每人最多 6 份**。全部在服务端执行。
- **上线前有两件事要先做**:当前未完成里的 P0「GHL 里由标签触发的工作流」盘点(重填会改学员的标签);
  以及 ⑩「结果没有记录 config 版本」—— 不先记版本,同一个人两份报告之间的差别分不清是「他变了」还是「我们改了题 / 文案」。
- 工作量估计 **7–9 个工作日**,分 5 步,每一步单独上线、单独验证、单独可回滚。

## 1. 数据结构

### 现在

| 表 | 主键 / 约束 | 含义 |
|---|---|---|
| `assessment_sessions` | `entitlement_id` **unique** | 一个人一份答题记录 |
| `assessment_answers` | `(session_id, question_id)` unique | 答案 |
| `assessment_survey` / `assessment_results` | 主键 `session_id` | 问卷、分数 |
| `assessment_report_files` | `(session_id, lang)` | PDF 与分享卡;Storage 路径是 `{session_id}-{lang}.pdf` |

答案、问卷、分数、报告文件**本来就挂在答题记录上**,不挂在人身上 —— 所以「一个人多份」只需要改 `assessment_sessions` 这一张表的约束,下面四张不用动。

### 改成

```sql
-- 示意,不是最终迁移
alter table assessment_sessions add column attempt_no int not null default 1;   -- 现有每一行都是第 1 份
alter table assessment_sessions drop constraint <entitlement_id 的 unique>;
alter table assessment_sessions add constraint sessions_attempt_unique unique (entitlement_id, attempt_no);
-- 同一个人同一时间最多一份没做完的 —— 由数据库保证,不靠代码记得
create unique index sessions_one_open_attempt on assessment_sessions (entitlement_id) where status <> 'completed';
-- 「每个人最新完成的那一份」—— 唯一的定义,所有统计都从这里取
create view assessment_latest_results as
  select distinct on (s.entitlement_id) r.*, s.entitlement_id, s.attempt_no
  from assessment_results r join assessment_sessions s on s.id = r.session_id
  where s.status = 'completed'
  order by s.entitlement_id, s.attempt_no desc;
```

- **`(entitlement_id, attempt_no)` 唯一**顺带保住了现在登录时「连点两次只建一份」的那条竞态保护(auth 的 get-or-create 依赖的正是原来那个 unique)。
- **「当前答题记录」**(cookie 指向谁)= 有没做完的就是那一份,否则是最新完成的那一份。现在 5 个函数各自 `.eq('entitlement_id').maybeSingle()`,
  一个人有两份时它们会 500;改成都调用同一个 `currentSession(entitlementId)`。cookie 本身不用改(它只装 entitlement id,不装答题记录 id)。
- **考虑过、不推荐的另一种**:仍然一人一份,重填时把旧答案、旧分数、旧文件复制进「历史表」,再把这一份清空重答。
  不推荐的理由:①要把一份已完成的答题记录**打回未完成** —— 正是那道守卫要防的事;②历史表是第二个真相源(判断标准 3);③PDF 的路径按答题记录 id 命名,清空重答会和旧文件撞名。

### 已有数据怎么迁移

- 迁移只做三件事:加列(默认 1)、换约束、建视图。**不改任何一行已有数据**,不碰 Storage。
- 迁移自带断言:跑完之后「每个 entitlement 恰好 0 或 1 份、全部 `attempt_no = 1`」,不成立就整条回滚(与 `20260812300000` 同一个做法)。

### 已经发出去的报告会不会因此改变(判断标准 19)

| 什么时候 | 谁的报告 | 会不会变 |
|---|---|---|
| 第一步上线(只有数据层) | 所有人 | **不变**。每个人只有一份,「最新的一份」就是它;基准线、批次统计、名单都逐字相同 —— 上线前后对生产做只读快照比对来证明,对不上就回滚 |
| 有人重填之后 | **重填的那个人** | 报告默认显示新的一份(这是需求本身);旧的一份留在「历次结果」里,PDF 原样可下载 |
| 有人重填之后 | 其他所有人 | 网页报告里「与全体平均比」的数字会微动 —— **与今天每多一个新学员完成测评时完全一样**。去重(一人只算最新一份)正是为了让它只是这种程度的变化;不去重的话,重填的人会被算两次,那才是改变了已发报告的含义 |
| 任何时候 | 所有人的 PDF | **不变**。PDF 是生成那一刻定下的 |

⚠️ 一个要接受的事实:旧的那一份网页报告里,「与全体平均比」是**按现在的全体学员**算的,不是按当时的 —— 与今天的网页报告是同一个性质(只有 PDF 冻结了当时的样子)。
建议在历史报告的页面上写一句「基准线按现在的全体学员计算;当时的版本见 PDF」。

## 2. 报告页

- **打开链接**:做过测评的人(至少有一份已完成)→ 直接到**最新完成的那一份**报告。第一次来的人照旧进答题页。
- **重填从哪里开始**(Viho 已定):背景题与问卷**预填上一次的答案**,可以直接确认或修改;15 道正式题从空白开始。
  (现在登录后的去向由那一份答题记录的状态决定;改成「有已完成的就去报告」。)
- **「重填」按钮**放在报告最下方。点了先弹确认框,说清楚四件事:旧报告会保留;新的一份会成为默认显示的那份;
  顾问那边看到的信息会更新成新的一份;下一次可以重填的时间。不满足频率限制时按钮是灰的,旁边写「X 月 X 日 X 点之后可以再重填」。
- **有一份重填没做完时**:打开链接仍然先看到最新完成的那份报告,顶部一条提示「你有一次重填还没做完 —— 继续 / 放弃」。
  放弃 = 删掉那份没做完的(它还没有分数、没有文件、没对外发过任何东西)。
- **历次结果**:有两份以上时,报告下方列出「第 n 次 · 完成时间(马来西亚时间)· 总分 · 档位」,当前看的那份标出来;点开看那一份的报告
  (`/report?attempt=n`,服务端核对它属于 cookie 里这个人)。只有一份时不显示这一块。
- **PDF 与分享卡:每一份都有自己的**(它们本来就按答题记录存,路径不会撞)。完成时照旧自动生成那个人语言的 PDF 与两张分享卡。
  **「生成另一种语言」只对最新那一份开放**(Viho 已定);历史那几份只提供已经生成好的文件下载 —— 成本有上限,也少一个要守的入口。

## 3. 哪一份算数(逐项建议)

| 项 | 建议 | 现在要改什么 / 风险 |
|---|---|---|
| **GHL 字段**(状态、总分、档位、最弱两维、问卷几项) | **最新完成的那一份**。每次重填完成就写一次 | 字段在 GHL 联系人上(一人一份),同步状态却记在每份结果上。**重试要只认最新的一份**:现在的重试按「没同步成功」挑行、不分新旧 —— 旧一份的失败重试晚于新的一份,就会把新数字盖回旧数字。改成:新的一份完成时,旧的那几份未完成的重试一律作废 |
| **GHL 标签** | **最新完成的那一份**,与第一次完成时同一套规则(加新的、去掉不再适用的,只碰 `assessment_` 前缀) | ⚠️ **标签变化可能触发 GHL 工作流给学员发消息** —— 这正是 P0「标签触发的工作流」还没盘点的那件事。**盘点完之前不开放重填**。另外要改:「上次打了哪些标签」现在记在每份结果上,新的一份读不到旧的那份,于是旧标签永远不会被去掉;改成记在人身上(entitlement),与标签实际所在的地方一致 |
| **基准线**(报告里「与全体平均比」、批次排名) | **每人只算最新完成的一份**(从那个视图取) | 不去重的话,重填的人被算两次,而且他自己的旧分数会把平均往他那边拉 |
| **批次统计 / 现场模式** | 每人最新一份;看板多显示一行「其中重填过的 N 人」 | 现场模式复用看板的数据,一起改 |
| **问卷洞察 / 高意向导出** | 每人最新一份 | 不去重的话,**同一个联系人会在高意向 CSV 里出现两次** —— 拿去做 GHL 分群就是发两遍消息 |
| **漏斗** | 不变,本来就按人算 | 名单与漏斗现在把答题记录当成「一个对象」嵌进来,一人两份时会悄悄变成数组、读出 undefined 而**不报错** —— 第一步就要改掉 |
| **后台名单** | 一人一行,显示最新一份;加一列「第 n 次」,点开看历次;「复制报告链接」「重新生成 PDF」作用在选中的那一份 | 名单 CSV 加「重填次数」一列 |
| **校准脚本** | 默认每人最新一份;加参数 `--attempt=first / latest / all` | 第一次的答案代表「上课之前的样子」,对校准有独立的价值,不应该丢 |
| **entitlement 状态**(pending → … → completed) | 不变。第一次完成之后一直是 completed,重填进行中也不倒退 | 状态阶梯本来就只往前走 |

## 4. 防滥用与成本

**每完成一次重填会发生的事**(数字来自生产库 2026-10-14 的只读汇总与分享会当晚的实测):

| 项 | 量 |
|---|---|
| 渲染 PDF + 两张分享卡 | 一次 Chromium 渲染,分享会当晚中位 8.7 秒(7.7–12.9) |
| 存储 | 约 **0.66 MB**(PDF 平均 505 KB + 两张 PNG 各约 82 KB)。**Storage 里的文件现在没有任何清理**,每一份都永久保留 |
| GHL | 1 次字段写入 + 最多 2 次标签调用;**标签一变就可能触发工作流、给学员发消息**(见第 3 节) |
| 学员另外点「生成英文版」 | 再一次渲染 + 0.66 MB |

**限制**(第 2、3 条 Viho 2026-10-14 已定;全部在服务端执行,不靠前端按钮变灰):

1. **同一时间只能有一份没做完的重填** —— 由数据库的唯一索引保证,连点、开两个标签页都建不出第二份。
2. **两次完成之间至少隔 24 小时**(≈ 每天最多一次)。理由:
   - 15 道题问的是生意的做法(怎么获客、怎么跟进、怎么成交),这些东西几天到几周才会变;
   - 同一天里连着重填,多半是在「试答案看分数」—— 那会让 GHL 标签来回翻(每翻一次都可能触发一条消息),也会把明显不真实的答案带进基准线;
   - 24 小时仍然允许「课后回去照着清单做了一件事,第二天再测」这种正当用法。
3. **每人最多 6 份**(第一次 + 5 次重填)。上限让最坏情况可算:6 × 0.66 MB × 两种语言 ≈ 8 MB / 人。真有人需要更多,以后再加一个「Admin 放宽」的按钮。
4. 链接被作废(`access_revoked_at`)的人不能重填;测试批次同样受限(只是 GHL 照旧跳过)。

**Viho 选了 24 小时**(没有选「24 小时内最多 2 次」):「课前做过一次、课上当场再做一次」而两次在 24 小时以内的,会被第 2 条挡住。
以后真要放宽,做第 3 条里那个「Admin 放宽」的按钮,不改这条规则。

## 5. 和「已完成的不能再写入」那道守卫的关系

现在的守卫(`guardSessionWrite`,答题与问卷的四个写入口都过它):页面带着自己的答题记录 id 来写;
**与 cookie 当前的那份不一致 → `session_changed`;那份已经完成 → `already_completed`**。

重填之后它照旧成立,而且要更强:

- **重填必须是一个显式的动作**:新加一个 `start_retake`(只认 cookie),检查「至少有一份已完成、没有没做完的、满足频率限制、链接没被作废」,
  然后**插入一行新的**(`attempt_no` = 最大值 + 1)。**任何一份已完成的答题记录都不会被改回未完成** —— 没有这条路径。
- 旧页面(比如还开着第 1 份的答题页)来写:它带的是第 1 份的 id,而 cookie 的当前那份已经是第 2 份 → `session_changed`;
  就算对得上,第 1 份已完成 → `already_completed`。两条都是现有的行为,不需要新写。
- **建议顺手加一道数据库层的保护**:答题记录的状态只能往前走(触发器拒绝 completed → 其它);已完成的那份的答案与问卷不能再写(触发器拒绝)。
  现在这条规则只活在两个函数里,第二道在数据库里 —— 代码哪天绕过了守卫,数据库还会拒。
- **登录**:做过的人不再新建答题记录(只在第一次时 get-or-create),只去报告页。

**先写、先看它们红的测试**(第 0 条:每一条都先对着「没有守卫 / 没有限制」的版本跑红):
- 第 2 份已开始之后,第 1 份的页面写答案 → 409 `session_changed`;第 1 份的 id 对上了也 → 409 `already_completed`
- 已有一份没做完时再 `start_retake` → 拒绝;两个并发的 `start_retake` → 只有一份建成(数据库索引)
- 距上次完成不到 24 小时 / 已满 6 份 / 链接已作废 → 拒绝,而且什么都没写
- 第 2 份完成前后,第 1 份的答案、分数、报告文件逐字不变(快照比对)
- 第 2 份完成后,GHL 的「上次标签」从人身上读到的是第 1 份打的那一组(于是旧的会被去掉)
- 第 1 份留着一个失败的 GHL 重试、第 2 份已完成 → 重试不再把第 1 份写回去
- 第 2 份开始时:背景题与问卷的初始值 = 第 1 份的;15 道正式题一道都没有;不提交问卷 → 不能出分(预填不算已答)
- 历史那一份请求「生成另一种语言」→ 拒绝,而且什么都没写

## 6. 分几步做、每一步怎么验证、工作量

**第 0 步 —— 前置(不写代码)**

- ✅ Viho 定了三件事(2026-10-14,[见上](#viho-的决定2026-10-14)):24 小时 / 6 份;另一种语言只给最新一份;背景题与问卷预填重答、正式题从空白开始
- **P0「GHL 里由标签触发的工作流」盘点完**(第 3 节;没盘点完不开放重填)—— 给 Viho 的清单:[`ghl-inventory.md`](ghl-inventory.md)
- **⑩ 选一种「记录 config 版本」的修法并先上线**(选定的修法与上线结果记在 PROGRESS 的 ⑩)

**第 1 步 —— 数据层 +「最新的一份」的唯一定义(对现有数据零变化)** ≈ 2 天

- 迁移(第 1 节);`currentSession()`;所有读者换成视图 / 这个函数(附录里的每一处);名单与漏斗的嵌套改成显式取最新一份
- 新加一道门:`assessment_sessions` 按 `entitlement_id` 取单行、或嵌套 `assessment_sessions` 的写法,只允许出现在那个函数里 —— 让「漏改了一处」在构建时红,而不是一人两份时 500(判断标准 12)
- 验证:上线前后对生产做只读快照 —— 看板(全部)、基准线、名单 CSV、四个校准脚本的输出 —— **逐字相同**;smoke。回滚:还原迁移 + revert(数据没被改过)

**第 2 步 —— 服务端的重填** ≈ 2–2.5 天

- `start_retake` 与放弃;频率限制;登录去向;报告 / 报告文件按 `attempt` 取(核对属于这个人);「生成另一种语言」只认最新一份;
  新的一份的预填(上一份的背景题与问卷,只读给 cookie 的本人);GHL 的「上次标签」挪到人身上、重试只认最新一份;数据库触发器
- 验证:第 5 节那组测试先红后绿 + 变异;对测试批次的一条 entitlement 走一遍(GHL 本来就跳过)

**第 3 步 —— 前端** ≈ 1.5–2 天
